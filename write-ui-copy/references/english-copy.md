# English interface copy

Use this reference for every English draft or review.

## Plain English

- Use everyday words, short sentences, and active voice. Treat a sentence over 25 words as a prompt to simplify, not as an automatic failure.
- Put the user's task or the most important information first.
- Use `you` for the user's action. Use `we` only when the acting organisation is clear and actually performs the action.
- Use sentence case. Do not end short headings, field labels, or button labels with a full stop; punctuate complete explanatory sentences normally.
- Prefer `can` for a real option and `need to` for a requirement. Use `must` only when the obligation genuinely needs that force.
- Avoid jargon and unexplained abbreviations. Keep a familiar acronym when the audience uses it; otherwise write the name out on first use.
- Use gender-neutral language such as singular `they` instead of `he or she`.
- Use simple contractions only when they fit the product voice and audience. Avoid contractions when users may have limited English or when the shortened form can be misread.

## Controls and links

- Start task links and buttons with a verb when that makes the outcome clearer, for example `Send application` or `Download invoice`.
- Make links describe their destination or result. Do not use generic labels such as `Click here`, `More`, or `Read more` without a specific object.
- Use `Skip` for an optional follow-up, `Cancel` only while an operation can still be cancelled, `Back` for the previous step, and `Close` for dismissing a completed or informational surface.
- Keep destructive labels specific, for example `Delete account`, and make the consequence clear before the final action.

## Errors and status

- Use the same key words as the field label so users can connect an error to its input.
- Say what is wrong and how to fix it. Avoid `please`, `sorry`, `oops`, `valid`, and `invalid` when a direct correction is available.
- Write different messages for missing, too short, too long, out-of-range, and wrong-format input when the distinction changes the fix.
- Keep inline errors and error summaries equivalent and meaningful when read on their own.
- Confirm the completed outcome rather than announcing generic `Success` or `Done`.
